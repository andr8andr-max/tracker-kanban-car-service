# Техническое задание
## Web-канбан для автосервиса

**Версия:** 1.0  
**Дата:** 06.10.2026

---

## 1. Цель проекта

Разработать адаптивное web-приложение для автосервиса — кастомный Kanban, функционально близкий к упрощённому Trello, но адаптированный под процесс приёма, диагностики, согласования и ремонта автомобилей.

Система должна обеспечить:
- единый Kanban-процесс обработки заказов;
- ролевую модель и настройку прав;
- работу с карточками заказов;
- автоматизацию чек-листов;
- учёт времени по этапам и паузам;
- историю обслуживания автомобиля по VIN;
- Telegram-уведомления сотрудников и клиентов;
- статистику и экспорт;
- интерфейс RU/EN;
- единую базу данных на сервере.

Отдельное мобильное приложение и PWA не требуются.

---

## 2. Пользователи и роли

Базовые роли:
1. Механик
2. Мастер
3. Диагност
4. Менеджер
5. Администратор

Для базовых ролей задаются стандартные права, но администратор может изменять права любой роли. Администратор имеет полный доступ.

Самостоятельная регистрация не предусмотрена. Администратор создаёт логин, временный пароль и назначает роль. Учётная запись без роли неактивна. При первом входе пользователь задаёт постоянный пароль.

---

## 3. Авторизация и восстановление

Необходимо реализовать:
- вход по логину и паролю;
- первый вход с установкой постоянного пароля;
- восстановление через Telegram;
- ручное восстановление администратором;
- блокировку учётной записи администратором.

Рекомендуется: HTTPS, безопасное хэширование паролей, серверная проверка прав, тайм-аут сессии, аудит входов и изменений доступа.

---

## 4. Языки

Поддерживаются русский и английский. Пользователь выбирает язык в профиле, настройка сохраняется. Администратор задаёт язык по умолчанию.

Системные элементы, ошибки, уведомления и интерфейс переводятся на RU/EN.

---

## 5. Kanban-доска

Одна общая доска для одного автосервиса. Все авторизованные пользователи видят все карточки; действия определяются правами. Есть фильтр **«Только мои»**.

Статусы по умолчанию:
1. Запись
2. Приём автомобиля
3. Диагностика
4. Согласование работ
5. В работе
6. Ожидание запчастей
7. Готово
8. Выдано
9. Отменено

Администратор может добавлять, удалять, переименовывать и менять порядок статусов.

Основной процесс:

`Запись → Приём автомобиля → Диагностика → Согласование работ → В работе → Ожидание запчастей → Готово → Выдано`

Разрешены возвраты и другие переходы для пользователей с соответствующими правами.

---

## 6. Карточка заказа

Каждый визит — отдельная карточка. Карточки не сливаются физически; история связывается через VIN.

### Данные автомобиля
- марка;
- модель;
- год;
- VIN;
- госномер.

### Данные клиента
- имя;
- телефон;
- Telegram.

### Данные заказа
- номер;
- описание проблемы;
- исходный список работ;
- итоговый список согласованных работ;
- типы работ;
- общий ответственный;
- исполнители по этапам;
- приоритет;
- общий срок;
- комментарии;
- чек-листы;
- история изменений;
- время по этапам и паузы.

**Стоимость не используется и не отображается.** Фото и файлы не нужны.

---

## 7. Номер заказа

Автоматический формат: `YYYY-NNNNNN`.

Пример: `2026-000001`.

Номер уникален; нумерация последовательная внутри календарного года.

---

## 8. Создание заказа

Менеджер или пользователь с соответствующим правом создаёт заказ. Карточка создаётся в «Запись». Неполные данные автомобиля/клиента допустимы.

Обязательное поле при создании: **госномер**.

После ввода госномера сразу выполняется поиск совпадений.

Можно:
- создать вручную;
- использовать существующую карточку как основу;
- использовать шаблон карточки.

---

## 9. Поиск и история автомобиля по VIN

### 9.1. Главный идентификатор

**VIN — единственный идентификатор, объединяющий историю автомобиля.**

Госномер используется только для поиска кандидатов.

### 9.2. Нормализация госномера

При поиске игнорируются пробелы, дефисы и регистр букв.

`А123АА77`, `а123аа77` и `А123АА 77` считаются одинаковыми для поиска.

### 9.3. Один найденный вариант

Показываются:
- госномер;
- VIN;
- марка/модель;
- имя клиента из последнего заказа;
- телефон из последнего заказа;
- дата последнего обращения.

Пользователь подтверждает или отклоняет объединение.

### 9.4. Несколько вариантов

Показывается список с теми же данными. Пользователь:
- выбирает нужную историю;
- либо выбирает **«Не объединять»** и создаёт новую ветку.

### 9.5. Если объединение по госномеру отклонено

Создаётся новая ветка истории. VIN можно добавить позже. Без VIN заказ нельзя перевести в «Готово».

### 9.6. Проверка VIN на этапе «Готово»

При переходе в «Готово»:
1. VIN обязателен.
2. При пустом VIN переход запрещён.
3. Если VIN уже существует в другой истории, переход блокируется.
4. Показываются данные найденной истории, включая VIN.
5. Пользователь выбирает:
   - **«Согласиться с объединением»**;
   - **«Изменить VIN»**.
6. До выбора перейти в «Готово» нельзя.

После подтверждения карточка прикрепляется к истории VIN, но остаётся самостоятельным заказом.

### 9.7. История VIN

В истории хранятся отдельные заказы одного автомобиля.

Пользователь с доступом к карточке видит **всю историю по VIN, начиная с самого нового заказа**.

Для каждого заказа отображаются:
- номер заказа;
- дата обращения;
- госномер на момент обращения;
- марка/модель;
- имя клиента;
- описание проблемы;
- список выполненных работ;
- ответственный;
- итоговый статус;
- возможность открыть полную карточку.

---

## 10. История госномеров

VIN постоянен. Если госномер меняется:
- новый становится текущим;
- старый сохраняется;
- сохраняется дата обращения со старым номером.

---

## 11. Клиенты и автомобили

- один клиент может иметь несколько автомобилей;
- один автомобиль может иметь несколько обращений;
- отдельная клиентская карточка не нужна;
- данные клиента хранятся в заказах;
- изменения имени/телефона текущего заказа не меняют прошлые заказы.

---

## 12. Ответственные и исполнители

Поддерживаются:
- один общий ответственный;
- отдельный исполнитель на каждом этапе.

Назначение вручную или автоматически по правилу/роли/загрузке. Правила настраивает администратор.

---

## 13. Приоритеты

Три уровня:
1. Обычный
2. Срочный
3. Критический

По умолчанию менять приоритет могут мастер и администратор. Права может изменить администратор.

---

## 14. Типы работ

Администратор создаёт типы работ. Каждый тип может иметь:
- шаблон карточки;
- связанные чек-листы;
- правила автоматического назначения.

При создании карточки тип работы можно не выбирать.

**После этапа «Диагностика»** уполномоченный пользователь может выбрать несколько типов работ. По умолчанию это менеджер и мастер; права может изменить администратор.

Типы работ можно добавлять и удалять и после начала выполнения.

При изменении:
- действие записывается в историю;
- чек-лист актуализируется;
- выполненные пункты не сбрасываются.

При удалении типа:
- невыполненные пункты исключаются из активного чек-листа;
- факт удаления сохраняется в истории;
- выполненные общие пункты не стираются из истории.

---

## 15. Чек-листы

Чек-листы зависят от типа работы и этапа. Шаблоны создаёт администратор.

Если выбрано несколько типов работ, система автоматически формирует общий набор пунктов. Совпадающие пункты объединяются.

Например, если три типа работ требуют «Снять передние колёса», в общем чек-листе создаётся один пункт.

После выполнения общего пункта он считается выполненным для всех типов работ, которым он нужен.

При добавлении нового типа:
- новые пункты добавляются;
- совпадения объединяются;
- выполненные пункты не сбрасываются.

Каждый пункт фиксирует пользователя, дату и время выполнения.

По умолчанию администратор определяет обязательность пункта в шаблоне. В конкретном заказе уполномоченный пользователь может изменить обязательность.

Чек-лист является информационным и сам по себе не блокирует перемещение между этапами, за исключением настроенных обязательных условий перехода в «Готово».

---

## 16. Условия перехода в «Готово»

Базово требуется:
- заполнен VIN;
- выполнены все обязательные пункты чек-листа;
- назначен ответственный.

**Администратор может настраивать обязательные условия**, поэтому этот список должен быть конфигурируемым.

---

## 17. Доска и карточки

На карточке на Kanban отображать:
- госномер;
- марку/модель;
- ответственного;
- приоритет;
- общий срок;
- прогресс чек-листа.

Просроченные карточки визуально выделяются.

Поддерживать drag & drop и фильтры.

---

## 18. Действия с карточкой

При наличии прав:
- создать;
- редактировать;
- переместить;
- назначить/сменить ответственного;
- изменить приоритет;
- изменить срок;
- просмотреть историю;
- добавить комментарий;
- добавить/изменить чек-лист;
- удалить;
- архивировать;
- дублировать;
- создать по шаблону.

---

## 19. Дублирование карточки

Создаётся новый заказ с новым номером.

Копируются:
- автомобиль;
- клиент;
- описание проблемы;
- типы работ;
- исходный список работ;
- согласованный список работ;
- чек-лист как основа нового заказа.

Не копируются:
- статус;
- история изменений;
- комментарии;
- старые сроки;
- ответственные;
- фактическое время;
- выполненность чек-листа;
- история автомобиля.

Новая карточка начинается в «Запись».

---

## 20. Согласование работ

При входе в «Согласование работ» менеджер/мастер получают Telegram-уведомление. Время начала согласования записывается.

Менеджер вручную фиксирует:
- согласовано;
- частично согласовано;
- отказано.

Также фиксируется, какие работы согласованы/отказаны.

При полном согласовании — автоматический переход в «В работе».

При полном отказе — автоматический переход в «Отменено».

При частичном согласовании можно редактировать список работ. Исходный и итоговый списки хранятся отдельно.

Уполномоченный пользователь может вручную перевести заказ на другой этап.

---

## 21. «Ожидание запчастей»

Отдельный полноценный статус.

Хранить ожидаемую дату поступления.

При входе ответственный получает Telegram-уведомление.

Если дата наступила, а заказ остаётся в статусе, он автоматически помечается как требующий внимания.

После получения запчастей сотрудник вручную возвращает заказ в «В работе».

Время ожидания:
- показывается отдельно;
- отдельно попадает в статистику;
- не входит в рабочее время.

---

## 22. «Отменено»

При отмене обязательна причина из заранее заданного списка.

Фиксируются:
- дата;
- время;
- пользователь.

Карточка остаётся на доске в «Отменено».

Её можно восстановить и вернуть в работу.

Клиент получает уведомление об отмене в Telegram.

---

## 23. Срок и просрочка

Используется **один общий срок на весь заказ**.

Отдельные сроки этапов не используются.

При просрочке:
- карточка визуально выделяется;
- уведомляется ответственный;
- уведомляется мастер/администратор;
- уведомления могут повторяться через настраиваемый интервал;
- заказ учитывается в статистике.

---

## 24. Учёт времени

Учёт непрерывный, по календарному времени 24/7.

При входе на этап запускается таймер, при выходе фиксируется окончание.

Для каждого этапа хранить:
- вход;
- выход;
- длительность.

### Паузы

На любом рабочем этапе можно вручную поставить паузу.

Для паузы фиксируются:
- кто поставил;
- начало;
- окончание;
- длительность.

После снятия с паузы таймер продолжается.

Отдельно рассчитываются:
- общее время заказа;
- время этапов;
- время ожидания запчастей;
- рабочее время без ожидания и активных пауз.

---

## 25. Telegram сотрудников

Используется один бот для всего автосервиса.

Токен задаётся администратором в системных настройках.

Сотрудник подключает Telegram из профиля через ссылку/подтверждение в боте. Система сохраняет Telegram ID.

Если Telegram не подключён:
- Telegram-уведомление не отправляется;
- в системе отображается «Telegram не подключён»;
- пользователю предлагается подключить Telegram.

Назначение заказа сотруднику без Telegram не блокируется. Он получает web-уведомление, а в карточке виден статус подключения.

---

## 26. Уведомления сотрудников

Поддерживать:
1. назначение;
2. изменение этапа;
3. изменение ответственного;
4. приближение срока;
5. просрочку;
6. новый комментарий;
7. изменение приоритета;
8. изменение/выполнение чек-листа;
9. новый заказ;
10. автомобиль готов;
11. системные уведомления;
12. настройку типов уведомлений по ролям.

Администратор управляет набором уведомлений для ролей.

---

## 27. Telegram клиента

Клиент привязывает Telegram через ссылку/код и подтверждение в боте. Сохраняется Telegram ID текущего заказа.

Telegram клиента используется только для привязки и уведомлений. Ответы через Telegram не нужны.

Клиент получает уведомления:
1. автомобиль принят;
2. требуется согласование;
3. результат согласования;
4. автомобиль в работе;
5. ожидание запчастей;
6. автомобиль готов;
7. автомобиль выдан;
8. заказ отменён.

Решение клиента по согласованию вносит менеджер вручную.

---

## 28. Web-уведомления

Должен быть центр уведомлений:
- непрочитанные;
- прочитанные;
- счётчик непрочитанных;
- история уведомлений;
- переход к связанной карточке.

---

## 29. Комментарии

Все пользователи с правом комментариев могут их добавлять.

По умолчанию автор может редактировать и удалять свои комментарии. Администратор может менять эти права.

При новом комментарии уведомление получают:
- общий ответственный;
- исполнители текущих этапов.

---

## 30. Поиск и фильтрация

### Поиск

Поиск:
- госномер;
- VIN;
- имя клиента;
- телефон;
- номер заказа.

Поиск по марке/модели отдельно не требуется.

### Фильтры

- этап;
- ответственный;
- приоритет;
- просрочка;
- срок;
- тип работ;
- дата создания;
- период;
- «Только мои».

Фильтры комбинируются. Есть сброс всех фильтров.

---

## 31. История изменений

Все изменения записываются автоматически:
- пользователь;
- дата;
- время;
- тип действия;
- объект;
- старое значение, если есть;
- новое значение, если есть.

Историю можно фильтровать по пользователю и типу действия.

---

## 32. Статистика

Нужны:
- завершённые заказы за период;
- среднее время от приёма до готовности;
- среднее время каждого этапа;
- просроченные заказы;
- текущие заказы в работе;
- загрузка сотрудников;
- количество автомобилей/заказов по сотрудникам;
- статистика по типам работ;
- динамика по дням/неделям/месяцам;
- произвольные периоды;
- фильтры по сотруднику/этапу/периоду/типу работ;
- отдельный просмотр для менеджера/администратора;
- отдельная статистика ожидания запчастей.

Не требуется отдельный показатель:
- количество автомобилей за период;
- среднее время каждого сотрудника;
- статистика по маркам автомобилей.

Статистику экспортировать в:

- CSV.

## 34. Административная панель

Администратор может:
1. создавать, блокировать и удалять пользователей;
2. назначать и менять роли;

## 40. Приёмочные сценарии

### Создание заказа
Менеджер вводит госномер → система ищет совпадения → показывает варианты → пользователь выбирает историю или новую ветку → карточка создаётся в «Запись».

### VIN позже
Карточка без VIN остаётся в работе → VIN вводится позже → на «Готово» система проверяет VIN → при совпадении показывает историю → пользователь подтверждает объединение или исправляет VIN → после выполнения обязательных условий переход разрешён.

### Несколько типов работ
После диагностики выбираются несколько типов → чек-листы объединяются → одинаковый пункт выполняется один раз и считается выполненным для всех соответствующих работ.

### Добавление новой работы
В «В работе» добавляется тип → новые пункты добавляются → совпадения объединяются → выполненные ранее пункты не сбрасываются.

### Ожидание запчастей
Карточка входит в статус → задаётся ожидаемая дата → время ожидания считается отдельно → после наступления даты без выхода из статуса заказ помечается как требующий внимания → после получения детали возвращается в «В работе».

### Просрочка
Срок истёк → карточка выделена → отправлены настроенные уведомления → заказ попал в статистику.

### Backup
Ежедневный backup создаётся автоматически → хранится 30 копий → администратор может вручную создать копию и восстановить выбранную с подтверждением.

## 42. Допущения, принятые при завершении брифинга

Чтобы не затягивать согласование, следующие параметры зафиксированы как разумные настройки по умолчанию:

1. Нумерация заказа начинается заново по календарному году.
2. Постоянный пароль задаётся при первом входе.
3. У системы один автосервис, одна организация и одна доска.
4. Время считается 24/7 по календарному времени.
5. Все карточки видны всем авторизованным пользователям.
6. Основная проверка прав выполняется на сервере.
7. Перед restore рекомендуется автоматически создавать аварийный backup.
8. Поиск VIN и госномера должен использовать индексы.
9. Время и даты хранятся с часовым поясом организации.
10. Окончательное удаление данных является отдельной защищённой операцией администратора.
11. При конфликтующих одновременных изменениях предпочтительно использовать защиту от перезаписи чужих правок.
12. Для фоновых задач (уведомления, просрочки, backup) используется планировщик или очередь, выбранная в зависимости от backend.

## 43. Итоговая бизнес-модель

**Заказ = самостоятельная карточка.**

**VIN = единственная связь между заказами одного автомобиля.**

**Госномер = инструмент поиска возможной истории, а не идентификатор объединения.**

**Чек-лист = автоматически формируемые операции по выбранным типам работ с объединением одинаковых пунктов.**

**Время = автоматический учёт по этапам с отдельными паузами и отдельным временем ожидания запчастей.**

**Telegram = уведомления и привязка сотрудников/клиентов.**

Основной путь:

`Запись → Приём автомобиля → Диагностика → Согласование работ → В работе → Ожидание запчастей → Готово → Выдано`

При этом все предыдущие визиты автомобиля сохраняются как отдельные карточки и объединяются в единую историю по VIN.
